# 类型实验：当《幕间》离开跑团

> **重构说明（2026-10-27 之后）**  
> 本文记录的是旧 `trpg/drama` 双模式时期的实验。当前代码已经统一为**单一推演引擎**：deed/effect 拆分、只有敌意举动触发回应、状态可见性、被动角色；`rules.mode` 已移除，两个 drama 预置文件也已删除。本文保留为历史实验记录；当前规则以 [`RULES.md`](RULES.md)、[`PROSE.md`](PROSE.md) 和 [`SCENARIO.md`](SCENARIO.md) 为准。

> 实验日期：2026-10-27  
> 模型：`deepseek-flash`（`thinking: auto`）+ `MiniMax-M3.1-Flash`（Anthropic 兼容，`effort: max/high`）  
> 运行方式：CLI 实际推演（非模拟），全部战报在 [`examples/genre-tests/`](../examples/genre-tests/)  
> 结论一句话：**能，但需要把“行动判定”从跑团语法里拆出来；世界、秘密、记忆、私密线索这套信息结构，反而比预想的更适合文学叙事。**

---

## 0. 先给结论

六个非跑团类型都跑出了可读的场景：家庭戏、日常群像、双人爱情、后台讽刺、日轻奇幻、玄幻网文。它们不是“把跑团副本换成一个文艺标题”，而是真的产生了另一种东西：一顿饭里的四副碗筷、一封没有地址的信、一只在便利店门口抖水的猫、两个拿错信封的人、一间魔王城门口的药店、一场退婚宴。

但默认模式仍然把每一次“递话、关心、坦白、帮助”当成一次任务检定，于是出现三类系统性错位：

1. **目标 = 攻击。** 只要一个行动指向另一个人，对方就获得一次“反应”，提示词里叫“来袭”，多人指向同一个人还会吃“围攻”惩罚。于是“两个人扶外婆坐下”会被算成“同时应对 2 个行动 −1”。
2. **行动 = 任务。** 琐事也要掷骰，失败又与叙事需要矛盾：陈见月“转身取回文件袋”判了平和失败，但旁白里她还是把文件袋拿进来了；她说出了离婚，却被判“意图没有达成”。真正的问题不是骰子，而是**“做没做到”与“有没有被接住”被压进了同一个判定**。
3. **幕形 = 沙盒。** 默认模式的前四场都停在 `maxBeats`，没有一场产生 `ending`；《表彰大会》停在一句“李秘书张了张嘴，没出声”，《晚饭》停在“末班车几点”。对跑团这是留钩子，对短篇这是没有写完。

我另外加了一个**可选**的 `rules.mode: "drama"` 原型（默认仍是 `trpg`，不改旧行为），并在《晚饭》《末班邮局》上用**同一个 seed** 做了 A/B；同时把模型切到 MiniMax-M3.1-Flash 做了跨模型验证。结果：

- 《晚饭》：放弃原举动 **0 → 6**，日常 DC **10 → 8**，结局 **无 → 有**；文字从 602–731 字降到 478–577 字，更克制。
- 《末班邮局》：放弃原举动 **0 → 4**，回应从 4 次增到 8 次，结局 **无 → 有**；最后一句从“谁都没把手收回去”变成“都在这儿。……没寄过一张。”
- 同样的 seed 下，角色实际掷出的 d20 完全一致；差异来自**他们选择继续还是放下原来的举动**，不是运气。
- 跨模型：MiniMax 能跑通开场/行动/裁定/回应和完整的网文第一刻，但 `effort: max` 在 resolution 阶段会想太久——两次在 16k/32k 上限下返回空正文；换 `high` 后 89–123 秒完成。跨模型细节见 §8。

所以我的判断是：**这套引擎可以用于其他类型，但“跑团模式”和“叙事模式”应该是两个合同，而不是同一套提示词换几个词。** 下面把证据、边界和改法写清楚。

## 3. 前四个类型里，什么真的成立了

### 3.1 《晚饭》：四副碗筷与一句尝不出的汤

这是最像“文学”的一场，也是最能说明引擎长处的一场。

开场总控把“第四副碗筷”放在桌子最靠外的位置，公开处境只写可观察的东西；每个人拿到的私密线索完全不同：

- 周美芬：手停在盐罐上，想不起自己放没放过盐——这三天第五次。
- 陈见月：母亲开门时先扶了一下门框；文件袋还在楼道里，21:47 的票还没退。
- 周阿婆：她其实认出了外孙女，但一认出来就要哭，所以低头撕橘子上的白丝。

这些线索不命令角色做事，只给感官和记忆。角色自己长出了行动：

> 周美芬舀了半勺汤，吹了两下，尝。她把勺子停在嘴边，眉头没动，也没松开，像是在等舌头给她一个说法。等来的只是含混。

这一句是 **d20 自然 1 + 感知 7 = 9，对 DC 10 平和失败** 的直接结果。失败没有变成灾难，而是变成“她尝不出咸淡”——一个与早期认知障碍完全咬合的细节。这是这套规则最文学的一刻：**软失败不是惩罚，是潜台词。**

状态系统也长出了很像小说的东西：

- `话没落地 −2`
- `心口一点影子 −1`
- `被按住的主动权 −2`
- `把桌子稳住了 +2`

它们会在下一刻进入检定，也会进入角色的自我认知。这比“攻击力下降”更像文学笔记。

这一场的真实文本在 [`examples/genre-tests/dinner.md`](../examples/genre-tests/dinner.md)。结尾停在这里：

> “妈，票是九点四十七的。待几天……这回我想多待几天。正好有件事，得当面跟你们说。”
>
> 周美芬的手还搭在盆沿。她像是听见了，又像是只听见了后半句。她拿起勺子，先给见月碗里舀了一勺，汤面上的油花被推开又合上。“先喝汤。”她说，“凉了就腥。”

没有解释父亲的死，没有揭穿诊断，也没有让谁原谅谁。**这是引擎自己写出来的，不是我在场景里预设的。**

### 3.2 《末班邮局》：一封信与两次没接住的话

双人戏是最严苛的测试：只要一个人对另一个人说话，`target_id` 就会触发反应；默认模式下，两个人每刻都在“互相攻击”。

但它仍然写出了很好的东西。程野的“职业性”与苏晚的“绕弯”都成立：

> “照收。地址没写的，也能寄——只要寄件人肯留下名字。”

> 苏晚的手停在半空，随即收回去，扶住伞柄。她把脸偏了一点，看向那排掉漆的铁皮信箱，像是在数编号。

这一场 8 条行动里 5 条平和失败。对冒险故事，这是“队伍运气很差”；对爱情故事，这恰好是“两个人都在错过”。有一刻苏晚问“收了我的信，谁替我记着它去过哪儿”，判定失败，旁白写：

> 她本来是备好一句轻的话的，说完就能笑着翻过去。现在那句话在喉咙里搁了浅。

**失败在这里不是“没做到”，而是“说出口了，但没被接住”。** 这正是下一节要谈的语义错位，也是这套系统最有潜力的地方。

### 3.3 《凌晨三点》：没有危机，也没有被强行加戏

这是我最担心的一场：一个没有反派、没有倒计时、没有事件的便利店夜班，引擎会不会自己发明一个劫匪？

没有。四刻里发生的事是：

- 小满用一根关东煮的肠把三个人圈到同一句话里；
- 老马蹲下给猫擦水，顺嘴问女孩的箱子；
- 林菌把箱子挪到身后，背对灯，接了母亲的电话；
- 汤烧干了，门被风吹开，小满用报纸塞门缝。

唯一接近“事件”的是手机震动和锅底焦味。没有枪、没有追车、没有突然的绝症。猫就是猫，不是象征，也没有魔法。

状态变化也保持在日常尺度：

- `场面热起来了 +2`
- `半截袖子湿着 −1`
- `话被接住了 +2`
- `箱子挡在身后 +2`

这一场证明：**引擎不会天然把一切推向危机；它推的是“下一步要做什么”，而这件事在安静的戏里也可以是“把肠推给猫”。**

### 3.4 《表彰大会》：喜剧节奏居然是对的

后台讽刺喜剧需要四个人的官腔、误解、抢话和体面。引擎的“同时行动 + 互相指向”在这里反而成了优势：

> 赵德贵把薄信封折了折，往中山装内兜里按——按到一半，听见掌声，手停在那儿。

> 老周笑呵呵的，抓一把瓜子搁到赵德贵空着的那只手边——那只手正按着薄封，没腾出来，瓜子就摊在桌面上堆成一小堆。

四个人的目标互相错位：厂长想体面，秘书想拖，老工人想领一只缸子，工会主席想平安退休。每一刻都有人抢话、有人打圆场、有人把信封推来推去。这不是“文学腔”，是真正的舞台喜剧。

它的问题也最明显：停在“李秘书抽出一角纸，张了张嘴，没出声”——一个很好的悬念，但不是一个短篇的结尾。

## 4. 机制诊断：哪里在跟文学打架

### 4.1 目标 = 攻击：关心也会触发“围攻”

代码事实：

- 任何 `target_id` 非空的行动，都会让目标进入 `runReactions`；
- 反应提示词的开头是“你察觉到有人正直接对你采取行动”；
- 同一个目标被多人指向时，每多一人 `−1`，叫“围攻”；
- 目标若继续原行动，原行动与反应各 `−2`，叫“多任务”。

证据：

- 《晚饭》第 2 刻，周美芬和陈见月同时扶外婆坐下。外婆的反应承受 `同时应对 2 个行动 −1`。文本里这是“两个人扶老人”，规则里这是“被两人围攻”。
- 《凌晨三点》第 2 刻，小满和老马同时给林菌递吃的。林菌的反应承受 `同时应对 2 个行动 −1`。文本里这是“两个人劝她吃口热的”。
- 《表彰大会》第 1 刻，赵德贵和老周同时向李秘书施压。这里的“围攻”反而成立——但它是靠语义巧合成立的，不是规则区分了敌意。

这不是措辞问题。**规则层没有“ hostile / non-hostile ”的概念**，所有指向都被当成对抗。对跑团，这是合理的简化；对家庭戏，它把“照顾”翻译成了“攻击”。

### 4.2 行动 = 任务：说出口与没被接住，被压进了同一个判定

最清楚的例子在《晚饭》第 1 刻：

- 陈见月的行动：“转身出门取回文件袋”，DC 10，d20 3 + 敏捷 5 − 2 = 6，平和失败。
- 旁白：她还是出门、把文件袋拿进来、夹在腋下、带回屋里。

另一个例子在第 3 刻：

- 陈见月的行动：“按住外婆的手，说出离婚的事”，对周阿婆的反应总值 22，总计 7，平和失败。
- 旁白：她说了——“我离婚了，工作也辞了”，只是“落得并不清楚”。

从规则看，这两条都是“意图没有达成”；从文本看，动作都发生了。旁白为了自洽，把失败解释成“没被接住”“没被听清”。这个解释在文学上是对的，但它**违反了收束提示词“严格遵守机械结果”的规则**，也说明机械层缺少一个区分：

```text
deed（你做了什么）      → 通常发生，不需要掷骰
effect（它有没有落地）  → 掷骰，决定被接住 / 被岔开 / 被误解
```

现在的 `ActionRecord` 把两者压成一条 `summary`，再用一个总分决定整条行动的成败。于是：
- 物理动作失败 → 东西没拿到，但叙事需要它被拿到；
- 言语动作失败 → 话没说出口，但叙事需要它被说出；
- 关心动作失败 → 对方没被扶起来，但叙事需要她坐下。

**这是本次实验里最值得改的一处。** 叙事模式可以用提示词缓解，但真正的解法是数据模型里把 `deed` 与 `effect` 分开。

### 4.3 “大成功”通胀：d20 + 能力 + DC 的刻度不适合文学

默认模式的结果分布：

| 场景 | 大成功 / 总行动 |
|---|---:|
| 凌晨三点 | 6 / 12 |
| 表彰大会 | 7 / 16 |
| 晚饭 | 3 / 12 |
| 末班邮局 | 1 / 8 |

“自然 20 或 margin ≥ +8”在冒险里是合理的；在 DC 10–15 的日常戏里，能力 6–8 的角色只要掷到 14–16 就“大成功”。于是：
- 小满说一句“这猫都进来避雨了” → 大成功；
- 老周递一把瓜子 → 大成功；
- 周阿婆把一只碗收进厨房 → 大成功（叙事模式里改成“意外地奏效”，仍然怪）。

UI 和战报会把这些词直接显示给作者。对写小说的人，这是最出戏的一层。叙事模式已经改了标签（`成立` / `没有接住` / `意外地奏效`），但没有改阈值；“意外地奏效”仍然可能出现得太频繁。

### 4.4 没有“最后一刻”：默认模式不会自己收尾

前四场默认 run 的 `ending` 全部是 `null`。原因不是模型不会写，而是**引擎没有告诉它这是最后一刻**：

- `buildResolutionPrompt` 只说“如果本刻产生了本场结局，填 ending；否则 null。不要在第 1 至第 3 刻结束本场。”
- 它不知道 `beat.index + 1 >= maxBeats`。
- `RunEngine` 在达到 `maxBeats` 后只是停止 CLI 循环，不会补一次收尾调用。

结果：
- 《表彰大会》停在“李秘书张了张嘴，没出声”——像一集电视剧的结尾，不像短篇；
- 《晚饭》停在“末班车几点？”——情绪对，但故事没有落点；
- 《凌晨三点》停在“换汤之前”——日常可以这样收，但读者不知道这是作者的选择还是系统的截断。

叙事模式加了 `finalBeat` 参数：第 4 刻时明确要求“这是本场最后一刻，ending 必须非 null”。两场都成功生成了收束标题、150–300 字终章和最后一个画面。这是本次改动里性价比最高的一处。

### 4.5 情绪状态被当成公开标签

状态系统生成的东西很像文学笔记：

> `话没落地`、`心口一点影子`、`被按住的主动权`、`手里握着不该念的名单`

但 `publicCards()` 会把**其他角色的所有状态名**放进行动提示词的“可见状态”里。也就是说，陈见月能看到母亲头上挂着“话没落地”，老马能看到林菌头上挂着“话被接住了”。这些不是可观察的物理状态，是内心天气。

对跑团，状态就是公开 buff；对文学，这直接把潜台词翻成了字幕。叙事模式现在只在 `publicCards` 和收束的“可观察状态”里隐藏 `kind === "emotion"` 的状态，但这只是硬编码；更干净的做法是给 `Condition` 加 `visibility: "public" | "private"`，情绪默认 private。

### 4.6 每个人都是主角：没有 POV、没有被动角色

引擎要求 2–6 名角色，**每个人每一刻都要宣告一个行动**，并且每个人都拿到完整的内心、秘密、记忆和私密线索。于是：

- 《晚饭》里 82 岁、记忆时好时坏的外婆，每一刻都有完整的内心独白和主动行动。这次效果很好，但它意味着这是一个**群像戏**，不是陈见月的第一人称。
- 如果作者想要“单主角 / 有限视角”，其他角色会拥有同等厚度的内心，视角会被摊平。
- 如果角色是昏迷、沉睡、缺席、只是被谈论的人，引擎仍然会给她生成行动。
- 书信体、双线交叉、不同地点并行，在局部 run 里做不到（`location` 是单一场所）；世界层可以做一些跨地点，但这次没有测。

这不是 bug，是引擎的组织形式：**它是一个“全员玩家”的圆桌，不是一个“叙述者 + 视角人物”的小说引擎。** 要在其他类型里走得更远，需要 `spotlight` / `pov` / `passive` 这类一等概念。

### 4.7 UI 与文案仍在跑团里

这次以 CLI 战报为主。可以看到的耦合：

- 战报默认写“故事停在 N 个时刻。潮声仍在，选择尚未结束。”——《晚饭》里没有潮声。已改成“有些话还没有落地。”
- 开场提示词的铁律第 7 条写“所有角色仍在灯塔范围内”——所有非灯塔场景都错。已改成“场所”。
- CLI 和 UI 仍显示“大成功 / 平和失败 / 反应 / 来袭 / 检定”。叙事模式改了 CLI 与 Markdown 的标签，Web UI 还没改。
- 叙事模式的 Markdown 战报已把幕后注改成“导演幕后注”，但 Web UI 仍写“总控”。

这些是表面层，但**它们决定了作者是在“读一篇小说”，还是在“看一张跑团记录”**。如果目标是文学写作工具，UI 至少应该提供“只看叙事 / 展开机制”的层级。

### 4.8 结构化输出的脆弱性

前 7 个 run 里有 4 个出现过至少一次 JSON 校验失败（其中 3 次发生在 `resolution`，停在 `error`；另 1 次在内部重试后继续）：

- 失败信息是“模型输出未通过结构校验：模型返回内容不是合法 JSON”；
- 停在 `error` 的 3 个需要 `--resume`；恢复后都能继续；
- 失败调用没有计入 `run.llm.failures`（只有在成功响应后才记账），所以统计上看不见。

这次加了两层小修：
1. `parseJsonLoose` 现在会用一个状态机修复字符串里的裸换行/控制字符；
2. 重试提示明确要求转义引号、把换行写成 `\n`。

但它不是根治。要长期跑长篇小说，应该在失败时把原始输出落盘、在重试时降 temperature/关 thinking，或者把“叙事正文”和“状态变更”拆成两次调用，降低单次 JSON 的复杂度。

## 5. 叙事模式 A/B：同一个 seed，不同的合同

### 5.1 改了什么

> 历史说明：`rules.mode: "drama"` 是重构前的可选模式；当前已移除，下面的对照只作为实验记录。

| 层 | `trpg`（默认） | `drama`（实验） |
|---|---|---|
| 开场 | 跑团总控；布置“必须做出反应”的瞬间 | 叙事导演；布置“值得停留”的瞬间，压力可以来自沉默/时间/礼数 |
| 行动 | 具体的、面向下一步的行动；危机时刻 | 旁人能看见的举动；一句话、一次沉默、一次靠近/退开 |
| 裁定 | DC 8–30 的跑团刻度；“如果对方站着不动，这一下有多难” | 日常 5–8，情感/关系 10–15，重大决定 16–20；“会不会被接住” |
| 回应 | 反应/来袭/围攻；继续或放弃原行动 | 回应/递到你面前/多人同时要求；继续或放下原举动 |
| 收束 | 严格遵守大成功/成功/平和失败 | 社交失败 = 没被接住/被岔开/被误解；说出口的话仍然发生 |
| 状态 | 所有状态对他人可见 | 情绪状态默认只属于本人 |
| 最后一刻 | 不知道是最后一刻 | `finalBeat` 明确要求 ending |
| 标签 | 大成功/平和失败 | 成立/没有接住/意外地奏效 |

实现位置：`src/llm/prompts.ts`、`src/engine/engine.ts`、`src/engine/scenario.ts`、`src/types.ts`、`src/render/markdown.ts`。测试：`tests/scenario.test.ts` 新增模式归一化；`tests/utils.test.ts` 新增 JSON 修复。

### 5.2 数字对照

| | 晚饭 trpg | 晚饭 drama | 邮局 trpg | 邮局 drama |
|---|---:|---:|---:|---:|
| 完成刻 | 4 | 4 | 4 | 4 |
| 目标行动 | 10/12 | 10/12 | 4/8 | **8/8** |
| 反应/回应 | 7 | 8 | 4 | **8** |
| 放弃原举动 | 0 | **6** | 0 | **4** |
| 非目标行动 DC 均值 | 10 | **8** | 11 | —（全部互相指向） |
| 平和失败 | 4 | 2 | 5 | 3 |

| 结局 | 无 | **有** | 无 | **有** |
| tokens | 129,295 | 129,730 | 84,483 | 102,728 |

### 5.3 同一个 seed 的证据

《晚饭》两场使用 `genre-dinner-01`。同一个角色、同一刻的 d20 完全相同：

| 刻 | 周美芬 | 陈见月 | 周阿婆 |
|---|---|---|---|
| 1 | trpg 1 / drama 放弃 | 3 / 3 | 7 / 7 |
| 2 | 6 / 放弃 | 20 / 放弃 | 19 / 19 |
| 3 | 15 / 放弃 | 6 / 放弃 | 16 / 16 |
| 4 | 5 / 放弃 | 15 / 15 | 10 / 10 |

《末班邮局》同样：程野第 1 刻 9、第 2 刻 1、第 3 刻 1，两场一致。

也就是说，A/B 的差异不是“今天骰子好”，而是**提示词改变了角色选择继续还是放下**。这是很干净的行为差异。

### 5.4 文本对照

默认《晚饭》第 3 刻：陈见月说“我离婚了，工作也辞了”，判定平和失败。旁白只能把它写成“落得并不清楚”：

> 那几句话和盆底磕在桌面上的闷响、和灶上余火的嘶声挤在一处，落得并不清楚。

叙事《晚饭》第 1 刻：陈见月递点心，判定“没有接住”。旁白写的是：

> 那句话里的玩笑没有被接住，掉在桌上，谁也没有去捡。

同样是失败，后者的因果关系更干净：**动作发生了，效果没发生。** 这不是靠更华丽的句子，而是靠把判定对象从“说没说”换成“接没接住”。

叙事《末班邮局》的结尾：

> “都在这儿。”他说，声音不高，手垂到身侧，“没寄过一张。”
>
> ……
>
> 苏晚把第一张信纸从信封里抽出来半寸，又推回去，没有打开第二封。她的手最后压在那叠纸的边沿上，没再动。

终章标题是“都在这儿，没寄过一张”，最后一个画面是两只手隔着一柜台没寄出的纸。这是默认模式没有给出的东西：**一个由角色选择长出来的结尾，而不是系统在第四刻截断。**

### 5.5 没解决的部分

叙事模式只是提示词层的适配，所以它没有改变：

- 目标行动仍然是对抗检定；
- 多人指向仍然有“多人同时要求 −1”；
- 情绪状态的隐藏是硬编码，不是 schema；
- 没有 POV、没有被动角色、没有跨地点；
- Web UI 仍显示跑团标签；
- 结局是“被要求写”，不是“由场景结构保证”。

它是**一个可用的原型**，不是终局。

## 6. 建议：从“能跑”到“适合写”

### 6.1 已经做了的（低风险，默认不变）

1. `rules.mode: "trpg" | "drama"`，默认 `trpg`。
2. 叙事模式的提示词分叉：开场、行动、裁定、回应、收束。
3. `finalBeat`：叙事模式在最后一刻强制 ending。
4. 情绪状态在叙事模式里对其他角色隐藏。
5. 战报/CLI 的叙事标签；通用收尾句；开场“灯塔”改为“场所”。
6. `parseJsonLoose` 的控制字符修复 + 重试提示。

### 6.2 下一步最值得做的（按性价比排序）

1. **把 `deed` 与 `effect` 拆开。**
   ```json
   {
     "deed": "我把文件袋从楼道拿进来",
     "effect": "母亲看见文件袋的角",
     "ability": "agility",
     "stakes": "她先看见那张预约单"
   }
   ```
   `deed` 默认发生；检定只决定 `effect` 是否被接住、被误解、被岔开。这会一次性解决 4.2 的大部分矛盾。

2. **把“反应”改成“回应”，并区分敌意/非敌意。**
   - 只有真正带有逼迫、伤害、夺取、欺骗的行动才进入对抗；
   - 关心、帮助、坦白、递东西不触发“围攻”；
   - 多人同时说话可以是“场面压力”，但不叫“围攻”。

3. **重做叙事模式的结果刻度。**
   - 日常动作不掷骰，或 DC 5；
   - 情感动作只掷“是否被接住”；
   - 取消“大成功”，自然 20 才给“意外地奏效”；
   - 平败只表示“没接住/被岔开”，不表示“没做”。

4. **状态可见性进入 schema。**
   ```json
   { "name": "话没落地", "kind": "emotion", "visibility": "private" }
   ```
   默认情绪 private，身体/物件 public。

5. **POV / 被动角色 / 聚光灯。**
   - `rules.pov: "chen_jianyue"`：只有 POV 角色有完整内心，其他角色只写可观察行为；
   - `rules.passive: ["zhou_apo"]`：被动角色不宣告行动，只在他人的行动里被触及；
   - 或者 `rules.spotlight: "rotating"`，每刻只让 1–2 人做主动行动。

6. **幕形。**
   - `rules.ending: "closed" | "open" | "epilogue"`；
   - 短篇默认 closed：maxBeats 到达时强制收束；
   - 长线/沙盒默认 open：保留钩子。

7. **UI 分层。**
   - 舞台只显示叙事、台词、时间；
   - “机制”折叠里才显示 DC、骰点、状态修正；
   - 叙事模式把“总控”改成“导演”，“检定”改成“落点/接住”。

### 6.3 更远的方向

- **单主角/有限视角**需要重新设计“谁在这一刻有行动权”，不是加一个布尔值能解决的。
- **书信体/双线/跨地点**需要场景调度层；世界层可能能承担，但这次没有测。
- **真正的“文学模式”**可能不是“跑团规则的变体”，而是另一套合同：场景 → 节拍 → 意象 → 选择 → 余波，而不是行动 → DC → 结果。
- **人类读者测试**：这次是我作为作者/读者在评判。下一步应该让 3–5 个不知道实验设计的读者盲评“哪一版更像小说”，否则“更好”只是我的口味。

## 8. 跨模型与新增类型：MiniMax-M3.1-Flash、日轻、网文

### 8.1 接入

MiniMax-M3.1-Flash 走 Anthropic 兼容接口：

```text
baseURL = https://api.minimax.cn/anthropic
POST    /v1/messages
headers x-api-key, anthropic-version: 2023-06-01
body    { model, max_tokens, system, messages, temperature,
          output_config: { effort: "max" } }
```

和 DeepSeek 的 OpenAI 兼容接口相比，有三个实际差异：

- 没有 `response_format: { type: "json_object" }`，JSON 只能靠提示词和解析器；
- 没有 `thinking: true/false`，只有 `output_config.effort = low|medium|high|xhigh|max`；
- `usage` 把缓存命中的输入单独记账；`completion_tokens` 里包含 thinking tokens。

项目里新增了 `AnthropicModel` 与 `createLanguageModel()`；`.env` 用 `LLM_PROVIDER=minimax` 切换。CLI 可以临时覆盖：

```bash
node src/cli.ts --scenario genre-web-novel --beats 1 \
  --provider minimax --model MiniMax-M3.1-Flash --effort max
node src/cli.ts --scenario genre-web-novel --beats 4 \
  --provider deepseek --model deepseek-flash
```

实际使用时把 MiniMax 的 `max_tokens` 下限调到 **32,000**、超时调到 **600,000ms**。这不是为了写更长，而是因为 `effort=max` 会把大量预算花在 thinking 上：16k 时曾出现 `stop_reason=max_tokens` 且**一个 text block 都没有**。

### 8.2 两个新场景

| 场景 | 类型 | 角色 | 这次测什么 |
|---|---|---|---|
| 《魔王城门口的药店》 | 日轻奇幻 / 喜剧 | 3 | 吐槽、讨价还价、食物、温柔的收束；没有战争场面 |
| 《退婚宴》 | 玄幻网文 / 退婚流 | 4 | 当众压迫、底牌、围观者、连续打脸；每一刻要有新筹码 |

手稿：

- [`genre-light-novel.json`](../content/scenarios/genre-light-novel.json)
- [`genre-web-novel.json`](../content/scenarios/genre-web-novel.json)

日轻的赌注是“明天正午要不要上战场”，但场景里真正的动作是熬糖、抓药、收过路费、承认“我想走”。网文的赌注是“退婚书落印之前”，场景里真正的动作是亮信、还玉佩、请长老验印、拔剑三寸。

### 8.3 跑法

- **DeepSeek**：《魔王城门口的药店》《退婚宴》各 4 刻，完整跑完；作为类型与文本基线。
- **MiniMax**：两个新场景各跑第一刻；《晚饭》再跑一刻做接口 smoke。
  - 《退婚宴》第一刻的 resolution 在 `effort=max` 下成功；
  - 《晚饭》的 resolution 在 `effort=max` 下两次返回空正文（16k/32k）；《魔王城门口的药店》的 max resolution 迟迟不返回，二者都改用 `effort=high` 完成该刻；
  - 其余调用（开场/行动/裁定/回应）均为 `effort=max`。
- 因此这是**第一刻的跨模型对照**，不是四刻全跑对照；两种模型使用不同 seed。

### 8.4 数据

| 场景 | 模型 | 完成刻 | 调用 | tokens | reasoning | 备注 |
|---|---|---|---:|---:|---:|---|
| 魔王城门口的药店 | deepseek-flash | 4 | 32 | 126,585 | 10,535 | 4 刻完整；无 ending |
| 退婚宴 | deepseek-flash | 4 | 36 | 163,303 | 20,593 | 中途 1 次 JSON 失败，resume 后完成 |
| 魔王城门口的药店 | MiniMax-M3.1-Flash | 1 | 10 | 58,314 | 33,119 | resolution 用 high；其余 max |
| 退婚宴 | MiniMax-M3.1-Flash | 1 | 14 | 93,894 | 49,493 | 第一刻 max；含第二刻开头的部分调用，第一刻完成时约 62.8k |
| 晚饭 | MiniMax-M3.1-Flash | 1 | 8 | 42,663 | 22,729 | resolution 用 high；其余 max |

MiniMax 单刻的 token 是 DeepSeek 单刻的约 2–3 倍，墙钟时间是约 5–10 倍。最慢的一次是 light novel 的一个 reaction：178 秒。`effort=max` 的 resolution 可以跑到 5–10 分钟仍不返回正文。

### 8.5 `effort=max` 的坑

这是这次跨模型测试最重要的运维结论：

- **max 不等于更适合结构化输出。** 在《晚饭》的 resolution 上，16k 和 32k 两个上限都出现了 `stop_reason=max_tokens` 且没有 text block；模型把全部预算花在 thinking 上。
- 换成 `effort=high` 后，同一 prompt 在 89 秒（晚饭）和 123 秒（药店）内返回了合法 JSON，文本质量没有明显下降。
- 《退婚宴》第一刻的 max resolution 成功了，说明这不是“max 永远失败”，而是**对某些 scene/JSON 组合会进入过度思考**。
- 一个实用的折中：**开场/行动/裁定/回应用 max，resolution 用 high 或 xhigh**；或者把 resolution 拆成“叙事正文”和“状态变更”两个更小的 JSON 调用。
- 另一个坑是 token 记账：Anthropic 风格的 usage 把 cache read 单独列出；如果不把 `cache_read_input_tokens` 加回 prompt，MiniMax 的成本会被严重低估。本项目的 `AnthropicModel` 已修正。

### 8.6 文本对照

**日轻**：同一个“亚兰来买不怕的药”，DeepSeek 让他绕：

> 他半靠柜台的姿势忽然失去了对象，只好自己把身子扶正，笑容顺势收成了“明白了，我等着”的那种。他的目光又一次飘向后门和后窗，飘得很轻，落了个空。

MiniMax 让他直接崩：

> “琳小姐，刚才说错了。我要的不是吃了就不怕，是能让人把‘我想走’说出口的药。哪怕只说一次——我现在就怕得要死，止痛药也请给我一剂。”

两种都成立：DeepSeek 更像“轻小说里的逞强与吐槽”，MiniMax 更像“把角色一脚踹到台前”。MiniMax 这一场三条行动全部成功（琳报价、亚兰承认、米娅拆账），DeepSeek 则是琳成功、亚兰和米娅平和失败——**MiniMax 的摩擦更少，DeepSeek 的尴尬更多**。

**网文**：DeepSeek 让萧尘先提一坛酒、卖关子：

> “林家主，三年不见，先别急着盖印。我这一坛酒，是特意带来给你贺喜的——你猜猜，里头装的是什么？”

MiniMax 让萧尘第一句就把信拍在案上：

> “林家主，落印之前，最好先看看这封信。敢读，还是不敢？”

林震天的应对也更“网文”：

> “验。此信若涉通敌，老夫有何不敢？三位长老，请同验纸张、笔迹与印鉴。……此事未清之前，谁也不准落印！”

MiniMax 的网文感更强：公开、快、多人同时下注、每一句都在抢话语权。DeepSeek 的版本更讲究“先礼后兵”的层次。对“退婚流”这种类型，MiniMax 的第一刻更接近读者预期。

但同一个 deed/effect 问题也被放大了：MiniMax 把萧尘“当众亮出通敌信”判成**平和失败**（19 对林震天回应 20），旁白却明确写着信已经摊在案上、长老开始验看。对网文读者，这明明是第一巴掌打响了；系统却报告“意图没有达成”。这就是 §4.2 在爽文里的代价：**读者感知的胜负与系统的意图判定不是一回事。**

### 8.7 类型结论

- **日轻奇幻**：引擎能写吐槽、食物、讨价还价和“明天要不要上战场”的温柔；但它的 POV 仍是全员的，每个人都在内心吐槽。对轻小说常见的“第一人称主角 + 周围人夸张反应”，需要 `pov` 或 `spotlight`。另外“大成功/平和失败”这种词会破坏轻喜剧的轻松感。
- **玄幻网文**：引擎的“同时行动 + 互相指向”几乎是天然的网文群像调度：每个人都在同一刻出牌，围观者会反应，目标会回应。它很适合“退婚宴”“宗门大比”“朝堂对质”这类场景。问题在于判定语义：爽文的“打脸”需要明确的场面胜负，而现在的“平和失败”可能让一次成功的亮底牌看起来像失手。网文模式需要把“面子/气势/围观者”做成可结算的资源，而不是只靠 DC。
- **跨模型**：DeepSeek 更克制、更场景化；MiniMax 更直接、更戏剧化，网文适配度更高。这个判断只基于 1–4 刻的样本，不能当排行榜。

## 9. 局限

- 两个模型、每类一个样本；LLM 本身有随机性。
- 场景是我为这次实验写的，作者水平会影响结果；这不是“给定任意小说都能跑”的证明。
- 12 个 run 里有 5 个出现过 JSON 校验失败（4 个 resume，1 个内部重试）；另有 MiniMax `effort=max` 在《晚饭》resolution 上的空正文（16k 与 32k 上限各一次，不是 JSON 错，是 thinking 耗尽）。token 与耗时包含这些重试；失败调用未计入 `run.llm.failures`。
- 这次以 CLI 为主，没有系统测试 Web UI 的叙事模式呈现。
- “更好看”是我的阅读判断，没有盲评；下一步应该做人类读者测试。
- 世界层没有做非跑团测试；家族史诗、年代群像这类“跨时间”的故事仍是空白，值得单独做一轮。

## 10. 一句话收束

《幕间》的信息结构——秘密、私密线索、主观记忆、公开事实、谁知道什么——本来就是小说家的结构；它的问题不在“世界不够文学”，而在**它仍然要求每个文学动作像一次攻击那样结算**。

把“做没做到”和“有没有被接住”分开，把“最后一刻”告诉模型，把情绪还给角色自己，这套引擎就能从“跑团模拟器”变成“场景推演器”。它不一定会替你写小说，但它可以在你不知道下一句该让谁开口的时候，替你把所有人的秘密、欲望和沉默同时摆在桌上。

## 11. 重构后补充验证（新引擎）

以下运行的是当前统一引擎，不是本文前面的 `trpg/drama` 实验：

- **《守夜》**（[`genre-vigil.json`](../content/scenarios/genre-vigil.json)，1 主动 + 1 被动，3 刻，DeepSeek）：
  - 周宁是唯一宣告举动的人；林素 `passive: true`，不生成举动、不进入回应回合；
  - 3 刻共 12 次调用 / 37,494 tokens；每刻 1 条举动、0 条回应；
  - 结果使用“落地/意外奏效/落空”；旁白没有写林素的内心，只写手指、呼吸、监护仪。
  - 战报：[`vigil.md`](../examples/genre-tests/vigil.md)
- **《退婚宴》**（新引擎 1 刻，DeepSeek）：
  - 4 个举动中只有敌意举动进入回应；萧尘被林震天、顾长歌敌意指向，获得一次回应；
  - 萧尘自己指向林震天的举动是挑衅而非强制，`hostile=false`，因此林震天没有单独的回应回合；
  - 结果使用“落地/落空”，回应总值 19 同时对抗两条敌意举动；
  - 战报：[`web-novel-newengine.md`](../examples/genre-tests/web-novel-newengine.md)
- **《守夜》MiniMax 复测**（`effort=max`，1 刻，4 次调用 / 24,087 tokens）：
  - 被动角色同样不宣告举动、不进入回应；resolution 在 max 下 58.9 秒完成；
  - 结果“意外奏效”；旁白只写“手指收拢过一次”，并明确“是否听见那句话，现场无从判断”；
  - 战报：[`vigil-minimax.md`](../examples/genre-tests/vigil-minimax.md)
- **《守夜》MiniMax 正文工作流**（`effort=high`，`--pov zhou_ning --person first`，2 次调用 / 7,148 tokens）：
  - 第一人称限知正文；使用周宁自己的“定金已收”秘密，没有进入林素的内心；
  - 正文：[`vigil-minimax-prose.md`](../examples/genre-tests/vigil-minimax-prose.md)
- **《守夜》正文工作流**（DeepSeek，`--pov zhou_ning --person first`，两步 2 次调用 / 9,544 tokens）：
  - 第一步把 3 个时刻整理成场景大纲；
  - 第二步写第一人称限知正文，只使用周宁知道的信息；林素的秘密与内心没有进入提示词；
  - 正文：[`vigil-prose.md`](../examples/genre-tests/vigil-prose.md)

这些运行验证的是当前框架的关键路径：deed/effect、敌意回应、被动角色、状态可见性、文字创作工作流。它们不是完整的长篇测试。

另有一个反向测试：双人、单地点、单截止时间的《末班渡轮》在 6 刻内没有自发产生 `ending`，截止时间过后渡轮仍停在渡口；见 [`CONVERGENCE-TEST.md`](CONVERGENCE-TEST.md)。这说明低复杂度能收窄场景，但当前引擎不能可靠地让故事自己停下。
